# Final Verdict

Date: 2026-06-01

## Direct Answer

The two goals are not fully achieved as blanket product claims.

| Claim | Verdict | Why |
| --- | --- | --- |
| Local library scanning is fast/stable and cover/lyrics are accurate | Scan stability passes on the supplied real corpus; speed is now strong on the warm-cache rerun; cover/lyrics accuracy still partial | After removing per-file canonicalization from the fresh-scan hot path, Lyne scanned the user-supplied 594-file / 23.14 GB local library in 1.180 s at the default 2-worker setting, indexed 593 media items, and used about 33 MB peak RSS. The SPlayer native scanner rerun indexed 590 in 2.175 s with about 93 MB peak RSS and much higher sampled CPU. Cover presence was strong; lyric accuracy was not measured. |
| Playback quality and DSP are controllable and clearly stronger than ordinary Electron players | Audio/DSP control base passes; the Electron comparison is now same-operation for scripted real-file playback, but product-experience superiority is still not fully proven | Lyne has native controls and DSP paths that the Electron fixtures lack, callback/processor tests pass, the selected native bench suite runs through cargo, the active-playback control probe toggles nine controls with `/state` readback, Lyne latency/stability probes pass smoke runs on real local FLACs, and Electron now has both realtime WebAudio and same-operation real-file baselines. The remaining gap is subjective/user-visible superiority and release installation proof. |

## Product Interpretation

Lyne has value if the product positioning is "native local music player with serious audio-engine controls." The codebase already has more technical audio control than a basic Electron/WebAudio player. The Electron offline and realtime baselines make that contrast concrete: ordinary Electron can run WebAudio filters quickly, and the new real-file baseline shows it can also play the same FLACs quickly for scripted load/play/seek/next operations. What it still does not expose are the native output and DSP guarantees Lyne is trying to sell. The active runtime probe now also shows Lyne controls are not just dead code: they can be changed during active playback and read back from server state. The Lyne latency and stability scripts further show real local FLAC playback can be measured for load/progress, seek convergence, next-track switching, underruns, CPU, and memory.

The risky part has shifted. "Local scan is stable on a real local corpus" is now credible for the supplied library. "Fast" is now credible for this corpus after the hot-path fix and default 2-worker rerun, including against the SPlayer native scanner baseline, while staying lighter on memory and CPU. "Cover accurate" should still be softened to "cover presence is strong and fixture sidecar cover is proven"; correctness needs a labeled corpus. "Lyrics accurate" remains unproven. "DSP controllable" is credible from source, tests, selected native benches, active playback readback, and short Lyne playback probes. The Electron baseline is now fairer at the operation level, so the stronger Lyne claim should lean less on raw load/seek latency and more on native output controls, DSP breadth, underrun diagnostics, long-run stability, UI clarity, and packaged release behavior.
